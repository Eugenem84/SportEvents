Architecture

Источник правды по домену и инвариантам. Продукт и статус — в README.md. Порядок работ — в DEVELOPMENT.md.

1. Главный принцип

Сервис не является «волейбольным ботом».

Он является backend-сервисом для мероприятий, на которые люди могут регистрироваться.

Волейбол — первый сценарий использования.

Поэтому используется термин event, а не game.

2. Основные сущности

V1:

Chat
ChatChannel
User
ChatAdmin
Event
Booking

Связь:

Chat 1 ─── N ChatChannel
Chat 1 ─── N ChatAdmin
Chat 1 ─── N Event
Event 1 ─── N Booking
User 1 ─── N Booking (как booked_by и как участник, если есть внешний ID)

Отдельные таблицы players и venues в V1 не нужны.

3. Chat

Chat — группа людей, для которой организуются мероприятия.

Это внутренняя сущность. Она не хранит идентификаторы мессенджера.

Пример:

Chat #17
"Волейбол Иваново"

chats
-----
id
title
created_at

4. ChatChannel

Связь внутреннего Chat с внешней беседой.

Даже если в V1 канал только VK, идентификатор беседы не кладётся в chats.
Иначе позже один Chat нельзя будет связать с несколькими платформами.

chat_channels
-------------
id
chat_id
platform          -- в V1: vk
external_chat_id  -- для VK: peer_id, например 2000000047
created_at

UNIQUE (platform, external_chat_id)

Одна внешняя беседа не может быть привязана к двум Chat.

Мероприятия одного Chat не видны в другом.

5. User

Участник мессенджера, который взаимодействует с сервисом.

Это не аккаунт сайта (логин, пароль, регистрация). Такие аккаунты в V1 не делаются.

Внутренний User нужен, чтобы хранить booked_by_user_id и администраторов, не привязывая бизнес-логику к from_id VK.

users
-----
id
display_name
created_at

user_identities
---------------
id
user_id
platform          -- в V1: vk
external_user_id  -- для VK: from_id
created_at

UNIQUE (platform, external_user_id)

При первом сообщении или нажатии кнопки identity находится или создаётся.

6. ChatAdmin

Кто может подключать беседу, создавать мероприятия и менять чужие записи.

chat_admins
-----------
chat_id
user_id

PRIMARY KEY (chat_id, user_id)

В V1:

* пользователь, успешно подключивший беседу, становится администратором этого Chat;
* сложные роли (модератор, владелец площадки) не делаются.

Проверка «это админ беседы VK» по API VK — только в адаптере, в момент подключения.
Дальше права проверяются по chat_admins.

7. Event

Конкретное мероприятие.

events
------
id
chat_id
starts_at          -- timestamptz, всегда UTC в БД
title
location           -- произвольная строка в V1, не отдельная сущность venue
capacity
created_at

capacity — максимум участников со статусом confirmed.

Свободные места не хранятся:

free_slots = capacity - confirmed_count

«Ближайшие мероприятия» считаются относительно UTC и форматируются для пользователя с явным часовым поясом чата или площадки.
Пока отдельного поля timezone нет: для V1 достаточно хранить starts_at в UTC и отображать в одном фиксированном поясе (например Europe/Moscow), пока все события одного Chat в одном городе.

Регулярные игры: расписание хранится не в Event, а в отдельной таблице `chat_game_slots (chat_id, weekday, minutes)`, где `weekday` — 0 = воскресенье (как `time.Weekday` и PostgreSQL `DOW`), `minutes` — время суток в поясе чата. «Создать игру» без даты берёт ближайший слот (`schedule.Next`), поэтому администратору не нужно каждый раз вводить дату и время. Порядок источников даты: явная дата в тексте → день недели словами → расписание чата → дефолт «завтра 19:00».

Изменение capacity:

* увеличивать можно;
* уменьшать ниже текущего confirmed_count в V1 нельзя — операция отклоняется.

Удаление event с активными записями в V1: только явное действие администратора; активные bookings переводятся в cancelled, promotion не выполняется.

8. Booking

Факт участия человека в мероприятии. Не обязательно «пользователь сам записался».

bookings
--------
id
event_id
player_name
phone                -- необязательно
user_id              -- NULL, если гость без identity
booked_by_user_id    -- кто создал запись, NOT NULL
status
created_at

Статусы:

confirmed
waitlist
cancelled

Очередь — не отдельная таблица.

Очередь = bookings со статусом waitlist, порядок FIFO по created_at, затем id.

Активная запись — status IN (confirmed, waitlist).

9. Игрок не обязан иметь аккаунт

Вася может добавить друга, которого нет в беседе:

player_name = "Ваня Петров"
user_id = NULL
booked_by_user_id = ID Васи

Каждый участник — отдельный booking.

Правила повторной записи:

* если у участника есть user_id — не больше одной активной записи на event для этого user_id;
* гость без user_id идентифицируется слабо (имя). В V1 не обещать строгую защиту от двух гостей с одним именем; повторную запись «себя» проверять только для identity.

Частичный уникальный индекс:

UNIQUE (event_id, user_id) WHERE user_id IS NOT NULL AND status IN ('confirmed', 'waitlist')

Транзакция с FOR UPDATE не заменяет этот индекс.

10. Кто может создавать Booking

* сам участник;
* другой участник (гостя);
* администратор.

Веб и другие клиенты — позже, через те же application services.

11. Внешние платформы

VK, MAX и Telegram не должны попадать в бизнес-логику.

External Platform
        ↓
Platform Adapter
        ↓
Internal Command
        ↓
Application Service
        ↓
Store
        ↓
PostgreSQL

Пример:

VK
 ↓
VK Adapter
 ↓
Command{
    ChatID,    -- внутренний
    UserID,    -- внутренний
    Action,
    EventID
}
 ↓
BookingService
 ↓
PostgreSQL

12. VK

VK Community — сообщество, от имени которого работает бот.

VK Conversation — групповая беседа. Беседа может существовать без сообщества.
Бот добавляется в существующую беседу.

Внешний идентификатор беседы: peer_id, например 2000000047.

Он хранится в chat_channels.external_chat_id, не в chats.

13. Регистрация беседы

Добавление бота в беседу и регистрация в сервисе — разные операции.

Администратор инициирует подключение, например:

@bot подключить

Адаптер извлекает platform=vk, external_chat_id, external_user_id.

После проверки прав:

1. найти или создать User по identity;
2. создать Chat;
3. создать ChatChannel;
4. добавить User в chat_admins.

Точные методы VK API — по актуальной документации VK.

14. Один backend — много бесед

Один VK-бот обслуживает много независимых Chat.

Мероприятия не пересекаются между беседами.

15. Конкурентная запись

Инвариант: confirmed_count <= capacity.

Внутри транзакции:

SELECT ... FROM events WHERE id = $1 FOR UPDATE;

Затем:

1. проверить существующую активную запись для этого user_id, если он есть;
2. посчитать confirmed;
3. вставить confirmed или waitlist;
4. commit.

Нельзя полагаться только на проверку в Go.

Повторная доставка одного и того же события VK не должна создавать вторую запись.
Идемпотентность: опираться на уникальность активной записи по user_id и, при необходимости, на event_id колбэка VK (если API его даёт). Не вводить отдельную таблицу «обработанных апдейтов», пока не понадобится.

16. Очередь и promotion

Нет свободных мест → waitlist.

Отмена confirmed:

cancel booking
    ↓
первый waitlist по created_at, id
    ↓
waitlist → confirmed

Уведомление после promotion:

* если у записи есть user_id с identity — уведомить этого пользователя (ЛС, если VK позволяет, иначе сообщение в беседу);
* если гость (user_id IS NULL) — уведомить booked_by и/или написать в беседу, что место получил гость с таким именем.

Молча продвигать гостя без уведомления нельзя.

Место (seat_no) — это номер в составе, а не порядок в базе.

* номер выдаётся при записи и не меняется: отменивший оставляет свой номер;
* освободившийся номер переиспользуется следующей записью, а поднявшийся из резерва получает именно освободившийся номер;
* в анонсе перечисляются только занятые номера (каждое место — с новой строки), свободные пропускаются: нумерация не сдвигается, а счётчика свободных мест в анонсе нет.

Отмена игры (events.status = 'cancelled') — не удаление.

* событие остаётся в базе: на него ссылаются записи и сообщение-анонс в беседе;
* все активные записи (состав и резерв) переводятся в cancelled, из резерва при этом никто не поднимается — поднимать некуда;
* номера мест сохраняются, поэтому анонс может показать, кто был записан (место = был в составе, без места = был в резерве);
* отменённая игра не входит в предстоящие, не принимает записи и не появляется в «игры»;
* отменить игру может только администратор беседы, и повторная отмена честно сообщает, что игра уже отменена.

17. Отправка сообщений

В V1 достаточно методов адаптера:

* ответить в беседу (peer_id / external_chat_id);
* при возможности отправить личное сообщение пользователю.

Не вводить интерфейс Messenger, пока нет второй платформы.
Когда появится — абстракция должна различать «сообщение в чат» и «уведомление человеку», а не один SendMessage(userID).

Ответы людям и записи в беседе разделены: нажатие кнопки отвечает человеку всплывашкой
(messages.sendMessageEventAnswer, показывается только ему), а в беседу уходит короткая строка
события («3 - Евгений», «3 - Евгений минус», «3 - Пётр из резерва»). Так беседа не превращается
в поток служебных сообщений, но происходящее остаётся прозрачным для всех.

Адресация сообщений в VK (проверено вживую 25.09.2026):

* в групповой беседе у сообщения нет отдельного id: messages.send с peer_id отвечает 0, а
  править и закреплять можно только по conversation_message_id (иначе 15 Access denied);
* поэтому анонс отправляется с peer_ids: в ответе приходит объект с conversation_message_id, и
  состав сразу перерисовывается через messages.edit; своих кнопок у анонса нет — «Иду» /
  «Не иду» живут на постоянной клавиатуре под полем ввода (если id всё же не назван, бот
  читает его из беседы, LastOwnConversationMessageID);
* прочитать чужую беседу нельзя (messages.getHistory — 15 Access denied, у getConversationsById
  last_conversation_message_id равен 0);
* клавиатуру под полем ввода беседа берёт у последнего сообщения бота, поэтому строку записи
  («3 - Имя») бот отправляет после правки анонса, а сам анонс правит пустым inline-набором
  кнопок: без inline VK понял бы набор как «убрать клавиатуру из чата» и кнопки исчезли бы
  сразу после записи;
* закреплять сообщения разрешено владельцу беседы; сообществу-администратору VK отвечает 925,
  поэтому закрепление — попытка, а не гарантия: отказ пишется в лог и не ломает запись. Там, где
  бот закрепить не может, анонс закрепляет администратор вручную, а бот продолжает обновлять то
  же сообщение (правка закреплённого сообщения работает).

18. Индексы V1

* chat_channels (platform, external_chat_id) — unique
* user_identities (platform, external_user_id) — unique
* events (chat_id, starts_at)
* bookings (event_id, status, created_at) — выборка состава и FIFO waitlist
* частичный unique на активные bookings по user_id (см. раздел 9)

19. Не использовать микросервисы

Первая версия — один Go-процесс и PostgreSQL.

Docker Compose: app, postgres.

Не добавлять без реальной необходимости:

* Kafka, RabbitMQ, Redis;
* Kubernetes;
* CQRS, Event Sourcing;
* микросервисы;
* ORM.

20. Будущее — не V1

Архитектура не должна мешать добавить MAX, Telegram, web, mobile, карту площадок, статистику, оплату, сложные роли.

Это не реализуется заранее.

Отдельная сущность Player или Venue — только когда имя/телефон на booking или строка location перестанут хватать.
