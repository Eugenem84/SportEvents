Development Guide

Цель

Рабочий сервис и учебный проект по Go backend.

Не генерировать весь проект сразу. Делать небольшие вертикальные срезы и понимать каждый слой.

Перед изменением модели сверяться с ARCHITECTURE.md. Если код ей противоречит — сначала объяснить конфликт.

Правила

1. Сначала простое решение. Не добавлять абстракции «на будущее» (Messenger, второй канал, Redis).

2. Бизнес-логика не зависит от VK:

   VK Adapter → Application Service → Store

3. SQL вручную, pgx, без ORM.

4. Для записи, очереди и гонок — сначала сценарий, потом код.

Пример:

capacity = 2
Иван → confirmed
Пётр → confirmed
Сергей → waitlist

После отмены Ивана:

Пётр → confirmed
Сергей → confirmed

Этапы

Этап 1. Минимальный Go-проект

go.mod, cmd/server/main.go, Dockerfile, docker-compose.yml.

Проверка: docker compose up --build

Этап 2. PostgreSQL и миграции

Таблицы по ARCHITECTURE.md:

* chats
* chat_channels
* users
* user_identities
* chat_admins
* events
* bookings

Сразу уникальные ограничения и индексы из архитектуры, не «добавим потом».

Этап 3. Event Store

Создание event, ближайшие по starts_at, получение по ID, принадлежность Chat.
starts_at хранить как timestamptz.

Этап 4. Booking Service

Запись, отказ при повторной активной записи для user_id, capacity, waitlist, отмена, promotion FIFO, гость без user_id, удаление администратором.

Транзакция и SELECT FOR UPDATE на event.

Этап 5. Тесты Booking Service

* свободное место, последнее место, нет мест;
* повторная запись того же user_id;
* гость (два разных имени на одно событие допустимы);
* отмена и promotion;
* уведомление: для гостя вызывается путь «сообщить booked_by / в чат», не тихий skip;
* конкурентная запись (два параллельных запроса, capacity не превышен);
* уменьшение capacity ниже confirmed — ошибка.

Этап 6. VK Adapter

Только после работающего домена.

* POST /vk/callback;
* confirmation и проверка secret;
* message и callback button;
* from_id → User / identity;
* peer_id → Chat через chat_channels;
* внутренние команды, ответ в беседу, keyboard;
* повтор того же действия не создаёт вторую активную запись.

Этап 7. Подключение беседы

бот в беседе → команда подключения → права → Chat + ChatChannel + ChatAdmin → ответ об успехе.

Этап 8. Список мероприятий

«Игры» → адаптер → Event Service → сообщение со списком.

Этап 9. Запись из VK

кнопка → BookingService → confirmed / waitlist → ответ в беседу.

Этап 10–11. Участники и админ

Добавить/удалить игрока, списки confirmed и waitlist, создание и изменение event, проверка chat_admins.

Этап 12. Расширение

После стабильного VK оценить MAX / Telegram / web. Не реализовывать заранее.

Локальный VK callback

VK не ходит на localhost. Нужен публичный HTTPS tunnel на локальный порт приложения.

Production: VK → HTTPS → VPS → Go.

Работа с Cursor

Помощник, не генератор репозитория целиком.

1. Прочитать ARCHITECTURE.md и текущий код.
2. Объяснить изменение.
3. Менять минимум файлов.
4. Показать diff и способ проверки.

Критерий готовности V1

1. Админ подключает существующую VK-беседу.
2. Админ создаёт event.
3. Участник видит event.
4. Участник записывается.
5. При заполнении следующий попадает в waitlist.
6. Участник отменяет запись.
7. Первый из waitlist становится confirmed и получает уведомление (гость — через booked_by или беседу).
8. Администратор добавляет человека вручную, в том числе гостя.
9. Администратор удаляет человека.
10. Всё в одной PostgreSQL database.
